# План: многопользовательский mcp-sql

Статус: реализовано (этапы 1-7: адреса, user.db, ключи, лимиты, очистка по сроку, бот, сайт, развёртывание). Документ сохранён как архив решений; актуальное описание лежит в `README_ru.md`.

Отличия реализации от плана:

- `user.db` лежит в `data/system/user.db`, время хранится числами (секунды от эпохи), таблицы `workspaces` нет: источником правды служат файлы `users/{id}/*.db`; добавлена таблица `user_state` (время последнего патча).
- Персональная страница по `statsToken` не делалась и не нужна: личные данные бот показывает в «Мои данные»; `statsToken` больше не выдаётся.
- Вместо `GET /api/me`: `GET /api/usage` (ключ записи) и внутренний `GET /internal/me`. Вместо `GET /api/stats` сервис отдаёт открытый `GET /public/stats`, а сайт проксирует его как `/api/stats`.
- Интервал между патчами считается на пользователя, а не на workspace. Счётчики пишутся в `user.db` сразу, без накопления в памяти.
- Сайт пока только на русском. Бот работает через long polling.
- Чистка по сроку: раз в минуту удаляются базы пользователей без живых ключей и каталоги неизвестных владельцев, затем строки истёкших ключей; при пустой `user.db` чистка ничего не удаляет.

## 1. Принятые решения

| Тема | Решение |
| --- | --- |
| Единица хранения | workspace = один файл SQLite (одна база Indexer). Внутри может быть несколько проектов (`project`) |
| Лимиты на пользователя | не больше 3 workspace, каждая база не больше 20 МБ |
| Замена | `push --db` в существующий workspace заменяет только его; остальные не затрагиваются. Четвёртый workspace отклоняется (409), автоудаления нет |
| Ключи | пара: ключ ИИ (чтение) и ключ пользователя (запись, может и читать); сроки 5 ч, 1 день, 7 дней |
| Жизнь баз | пока активна пара ключей; при истечении без продления все базы пользователя удаляются |
| Продление | новая выдача ключей в боте заменяет пару и продлевает жизнь баз |
| Вход | только Telegram-бот: `/start`, выбор срока, бот присылает два ключа и персональную ссылку на статистику |
| Лимит выдач | N в день (по умолчанию 5); команда сброса (revoke всех ключей и удаление баз) доступна всегда и обнуляет счётчик выдач |
| Потолок | 50 пользователей с активной парой ключей; при превышении бот отвечает «лимит сервера исчерпан, зайдите позже» |
| Администрирование | только лимиты и ограничения; подробности смотрите SQL-запросами к `user.db` на сервере |
| Сайт | статический модуль `mcp-sql-web`, английский по умолчанию и русский; публичная статистика и персональная страница; без личного кабинета |
| Бот | отдельный Gradle-модуль и отдельный контейнер; в `user.db` напрямую не пишет, работает через внутренний API сервиса |
| Локальный запуск | режим `local` (один пользователь, ключи из переменных окружения, как сейчас) для opencode и разработки |

## 2. Адреса

MCP (ключ чтения или записи):

- `/mcp` — все workspace пользователя; аргумент `workspace` нужен, если их несколько (как сейчас).
- `/mcp/{workspace}` — выбранный workspace.
- `/mcp/{workspace}/{project}` — выбранный проект внутри workspace.

В двух последних вариантах значения из пути главные: аргументы `workspace` и `project` инструментов игнорируются или должны совпадать.

API (ключ записи), существующие пути сохраняем, чтобы не ломать `push`:

- `GET /api/workspaces` — список workspace пользователя.
- `GET /api/workspaces/{workspace}` — информация.
- `PUT /api/workspaces/{workspace}/db` — загрузка базы (заменяет workspace).
- `POST /api/workspaces/{workspace}/patch` — патч.
- `DELETE /api/workspaces/{workspace}` — новое: удаление.
- `GET /api/me` — новое: лимиты, остатки, срок ключей, workspace (ключ чтения или записи).
- `GET /api/stats` — новое, без ключа: публичная статистика.
- `GET /api/stats/{statsToken}` — новое, без ключа: данные для персональной страницы (токен из ссылки бота).
- `GET /health` — как сейчас.

Внутренний API (только для бота, заголовок `X-Internal-Key`, наружу не публикуется):

- `POST /internal/keys` — выдать пару ключей (`tgId`, срок); ответ: ключи и ссылка статистики (показываются один раз).
- `POST /internal/reset` — отозвать ключи и удалить базы пользователя.
- `GET /internal/users/{tgId}` — статус пользователя.
- `GET /internal/expiring?withinMinutes=N` — кому отправить предупреждение.

## 3. user.db

Файл `data/user.db` (WAL), пишет только сервис.

```sql
CREATE TABLE users (
  id INTEGER PRIMARY KEY,
  tg_id INTEGER NOT NULL UNIQUE,
  created_at TEXT NOT NULL,
  banned INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE key_pairs (
  id INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id),
  ttl_kind TEXT NOT NULL CHECK (ttl_kind IN ('5h','1d','7d')),
  read_hash BLOB NOT NULL UNIQUE,
  write_hash BLOB NOT NULL UNIQUE,
  stats_hash BLOB NOT NULL UNIQUE,
  created_at TEXT NOT NULL,
  expires_at TEXT NOT NULL,
  revoked_at TEXT
);
CREATE INDEX key_pairs_user ON key_pairs(user_id, expires_at);

CREATE TABLE workspaces (
  id INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id),
  name TEXT NOT NULL,
  size_bytes INTEGER NOT NULL,
  db_id TEXT,
  seq INTEGER,
  languages TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  last_patch_at TEXT,
  UNIQUE (user_id, name)
);

CREATE TABLE usage_daily (
  user_id INTEGER NOT NULL REFERENCES users(id),
  day TEXT NOT NULL,
  uploads INTEGER NOT NULL DEFAULT 0,
  upload_bytes INTEGER NOT NULL DEFAULT 0,
  patches INTEGER NOT NULL DEFAULT 0,
  requests INTEGER NOT NULL DEFAULT 0,
  response_bytes INTEGER NOT NULL DEFAULT 0,
  key_issues INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (user_id, day)
);
```

Правила:

- Ключи генерируются из 32 случайных байт; в базе только SHA-256. Показываются один раз.
- День считаем по UTC.
- Счётчики запросов копятся в памяти и сбрасываются в `usage_daily` раз в несколько секунд, чтобы не писать в SQLite на каждый запрос.
- Файлы баз: `data/users/{userId}/{workspace}.db`. Имя проверяется `ProjectNames.isValid`, итоговый путь нормализуется и проверяется на принадлежность каталогу пользователя.

## 4. Лимиты (`application.yml`, `mcpsql.*`)

| Параметр | Значение |
| --- | --- |
| `max-workspaces` | 3 |
| `max-db-mb` | 20 (на распакованную базу, в том числе после патча) |
| `uploads-per-day` | 10 |
| `upload-bytes-per-day` | 300 МБ (полные загрузки и патчи вместе) |
| `patch-interval-seconds` | 30 на workspace |
| `requests-per-day` | 5000 вызовов инструментов MCP |
| `key-issues-per-day` | 5 (сброс обнуляет) |
| `max-active-users` | 50 |
| `min-free-disk-mb` | 2048 (ниже порога: новые пользователи и загрузки получают 503, чтение работает) |
| `max-response-chars` | 8000 (уже есть) |
| `sql-timeout-seconds` | 3 (уже есть) |
| `sql-max-rows` | 200 (уже есть) |
| `max-upload-mb` | 200 → заменить на `max-db-mb` |

Расчёт трафика с реальным лимитом ответа 8000 символов: 5000 запросов дают порядка 40–80 МБ исходящего в сутки на пользователя, а загрузки до 300 МБ. Для 50 пользователей в худшем случае это около 17 ГБ в сутки, обычно намного меньше. Дополнительно оставляем сервисные пороги по суммарному трафику из переписки.

## 6. Тесты изоляции (обязательные)

1. Пользователь A не получает базы B ни через `/mcp/{workspace}`, ни через аргумент `workspace`, ни через `sql`.
2. Имена с `..`, `/`, `\`, пробелами, очень длинные, регистр: ошибка или 404, файл вне каталога пользователя не читается.
3. Чужой и несуществующий workspace возвращают одинаковый ответ 404.
4. Ключ чтения не может `PUT`, `POST`, `DELETE`.
5. Просроченный, отозванный и забаненный ключи не принимаются сразу после события.
6. Четвёртый workspace, база больше 20 МБ, патч, увеличивающий базу выше 20 МБ, распаковка архива-бомбы: отказ, старое состояние сохраняется.
7. Патч чаще, чем раз в 30 секунд: 429.
8. После истечения пары базы удалены, а выдача новой пары начинает с пустого состояния.
9. `sql` не читает другие файлы (нет `ATTACH`, расширений, записи).

## 7. Этапы

1. **Основа**: режим `local` и `multi`, интерфейс аутентификации, `user.db`, путь `/mcp/{workspace}/{project}`, изоляция по пользователям, квоты, удаление по сроку, тесты раздела 6. Результат: сервис работает как сейчас для режима `local`.
2. **API**: `DELETE`, `/api/me`, публичная и персональная статистика, внутренний API; тесты на лимиты.
3. **Indexer CLI**: понятные сообщения для 401, 409, 413, 429, 503; подкоманда удаления workspace; проверка размера до загрузки (подсказка про `--no-source`).
4. **Бот** (`mcp-sql-bot`): long polling через JDK `HttpClient` без Spring (меньше памяти); команды `/start`, выбор срока, сброс, статус; предупреждение перед истечением; обращения только к внутреннему API.
5. **Сайт** (`mcp-sql-web`): статические страницы (главная, документация с примерами `curl` и коллекцией Postman, публичная статистика, персональная страница по токену), `config.js` с адресом API, английский по умолчанию и русский; образ на базе Caddy как один из вариантов развёртывания.
6. **Выпуск**: Compose с лимитами памяти (оценки: сервис около 256 МБ кучи, бот около 96 МБ; замерить), ротация журналов Docker, резервная копия `user.db`, README и правила использования, нагрузочная проверка, обновление сервера.

## 8. Риски и проверки

- Стабильность пересылки `/mcp/{workspace}/{project}` в Spring AI: проверить тестом до остального.
- Память двух JVM на 1 ГБ: замерить, при нехватке уменьшить кучу или объединить процессы.
- Telegram: долгий опрос одним экземпляром бота; токен бота хранится только в `.env` контейнера бота.
- Учёт трафика хостера не совпадает с учётом сервиса: сверять по панели хостера и `vnstat`.
